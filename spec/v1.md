This document defines the specification for **Workflow Objects** and **Workflow Declarations** in Ballerina. It introduces a structured approach to orchestration, computational determinism, and event correlation within the language.

## 1\. Introduction {#1.-introduction}

### 1.1 Goals {#1.1-goals}

The primary goal is to establish a robust foundation for workflow objects and declarations that:

- Supports long-running, stateful business processes  
- Provides event correlation for mapping external signals to workflow instances  
- Accommodates future enhancements (new keywords, core concepts) without breaking changes

### 1.2 Design Philosophy {#1.2-design-philosophy}

Workflows are introduced as a subtype of objects, leveraging existing object-oriented semantics (fields, methods, visibility) while adding workflow-specific semantics and restrictions. (The semantics and rationale will be explained later.)

A **Workflow Object** is a structural subtype of the object type, distinct from:

- **Service objects** — which handle inbound network calls via listeners  
- **Client objects** — which handle outbound network calls

This approach provides familiar syntax while enabling specialized workflow behavior such as suspension and resumption.

### 1.3 Core Concepts {#1.3-core-concepts}

A workflow consists of four key components:

| Component | Description |
| :---- | :---- |
| **Workflow Logic** | The main orchestration flow (business process) |
| **Activities** | Atomic units of work (computation or I/O) |
| **Events** | External signals that the workflow can receive |
| **Correlation** | Mapping external data to specific workflow instances |

### 1.4 Timeline {#1.4-timeline}

The workflow implementation will be carried out in two phases:

1. **Phase 1:** Focuses on the core Workflow Logic and Activities.  
2. **Phase 2:** Will address Events and Correlation.

Find details [here](#8.-implementation-plan). 

## 2\. Workflow Declaration Example {#2.-workflow-declaration-example}

Before diving into the detailed specification, here is a complete example demonstrating a workflow declaration:

**Example: Simple Order Processing Workflow (Phase 1\)**

```java
import ballerina/http;
import ballerinax/temporal;


// --- Type Definitions ---
type OrderRequest record {|
    string id;
    string item;
|};

// --- Workflow Declaration ---
workflow orderFlow on new temporal:Engine() {

    // Workflow State
    string status = "NEW";

    // Execute Method - Entry point and main orchestration logic
    execute function process(OrderRequest req) returns string|error {
        self.status = "PROCESSING";

        // Activity Call - Invoke isolated unit of work
        int stock = check self->checkInventory(req.item);

        if stock > 0 {
            self.status = "COMPLETED";
            return "Order completed successfully";
        }
        self.status = "FAILED";
        return "Order failed: Out of stock";
    }

    // Activity Method - Isolated unit of work
    activity function checkInventory(string itemId) returns int|error {
        // External service call or database query
        return 10;
    }
}

// Usage Example

service /orderService on new http:Listener(8080) {

    resource function post placeOrder(OrderRequest req) returns string|error {
        // Start a new workflow instance
        string workflowId = check orderFlow->process(req);
        return workflowId;
    }
}   
```

**Example: Order Processing Workflow with an interruptible payment event (with correlation \- Phase 2\)**

```java
import ballerina/http;
import ballerinax/temporal;

// --- Type Definitions ---

type OrderRequest record {|
    string id;
    string item;
|};

type PaymentMsg record {|
    string orderRef;
    decimal amount;
|};

// --- Workflow Declaration ---

workflow OrderFlow on new temporal:Engine() {

    // Workflow State
    string status = "NEW";

    // Execute Method - Entry point and main orchestration logic
    execute function process(OrderRequest req) returns string|error {
        self.status = "PROCESSING";

        // Activity Call - Invoke isolated unit of work
        int stock = check self->checkInventory(req.item);

        if stock > 0 {
            // Event Receive - Wait for external signal
            PaymentMsg payment = check self<-paymentReceived;
            self.status = "COMPLETED";
            return "Order completed successfully";
        }

        self.status = "FAILED";
        return "Order failed: Out of stock";
    } resolve {
        // correlation key extraction and setting as key.
        return req.id;
    }

    // Activity Method - Isolated unit of work
    activity function checkInventory(string itemId) returns int|error {
        // External service call or database query
        return 10;
    }

    // Event Method - Interface for receiving external signals
    event function paymentReceived(string orderRef, decimal amount) returns PaymentMsg|error {
        // Validation logic
        if amount <= 0 {
            return error("Invalid payment amount");
        }
        return { orderRef: orderRef, amount: amount };
    } resolve {
        // correlation key extraction
        return orderRef;
    }
}

// Usage Example

service /orderService on new http:Listener(8080) {

    resource function post placeOrder(OrderRequest req) returns string|error {
        // Start a new workflow instance
        string workflowId = check OrderFlow->process(req);
        return workflowId;
    }

    resource function post payment(string orderId, decimal amount) returns string|error {
        // Send payment event to the workflow
        check OrderFlow->paymentReceived(orderId, amount);
        return "Payment received";
    }
}
```

### 2.1 Interacting with the Workflow {#2.1-interacting-with-the-workflow}

**Starting a workflow instance:**

```
// Returns the correlation key (string) or error
string workflowId = check OrderFlow->execute(orderRequest);
```

**Sending an event to a workflow:**

```
// Send payment event to the workflow (async signal)
check OrderFlow->paymentReceived("order-123", 99.99d);
```

## 3\. Workflow Semantics {#3.-workflow-semantics}

The following section elaborates on how workflow concepts are modeled as a subtype of object type.

### 3.1 Workflow Type Descriptor  {#3.1-workflow-type-descriptor}

- A workflow object is a **subtype of object** basic type.  
- It is **not** a service object or a client object  
- A workflow object type is defined by the presence of the `workflow` qualifier  
- Workflow objects can have additional member types: `execute`, `activity`, and `event` methods  
- Resolvers are not part of the type system; they are binding constructs that associate with the implementation of the object.

**Example** 

```java
public type OrderProcessType workflow object {
    // Fields
    string status;

    // Execute Method
    execute function startProcess(OrderRequest req) returns string;

    // Activity Methods
    activity function checkInventory(string itemId) returns int;
    activity function processPayment(PaymentInfo info) returns boolean;

    // Event Methods
    event function paymentReceived(string orderId, PaymentMsg msg) returns error?;
};
```

### 3.2 Workflow Class Definition {#3.2-workflow-class-definition}

A workflow class encapsulates state (fields), orchestration logic (execute), atomic operations (activities), and external signal interfaces (events).

```java
public workflow class OrderProcessor {

    // Fields
    string status;

    // Execute Method
    execute function process(InputData data) returns OutputData {
        // Orchestration logic
    } resolve { // Optinal
	// Define correation key
    }

    // Activity Methods
    activity function doTask(string input) returns int {
        // Atomic unit of work
    }

    // Event Methods
    event function onSignal(string correlationId, SignalData data) returns error? {
        // Signal handling logic
    } resolve {
	// Optional correation key derive. 
    }
}
```

### 3.3 Workflow Members {#3.3-workflow-members}

New workflow object members have specialized semantics that differ from standard object methods:

1. To represent different life cycles of the workflow with different semantics.  
2. To maintain consistency with other object subtypes and enable object sub-typing.

#### 3.3.1 Execute Method

The execute method serves as the **entry point** and contains the **main orchestration logic** of the workflow.

```
execute-method-decl :=
   metadata execute-method-quals
   function execute-method-name function-signature ;

execute-method-quals :=
   execute-qual function-quals
   | isolated-qual [transactional-qual] execute-qual
   | transactional-qual [isolated-qual] execute-qual

execute-qual := execute

execute-method-name := identifier
```

An optional `resolve` block is allowed after `method-defn-body`.

##### Semantics

| Property | Specification |
| :---- | :---- |
| **Cardinality** | Exactly one execute method per workflow object |
| **Visibility and Scope** | Implicitly public; the only method callable to initiate a workflow Defined in a separate symbol scope within the object.  |
| **Return Type** | Represents the result of a workflow. Must be a subtype of `anydata|error.`  |
| **Parameters** | Represents the input of the workflow Must be subtypes of `anydata` |
| **Resolver** | Allows an optional resolver block |

##### Restrictions

The execute method operates in a **restricted symbol scope**:

- Can only access workflow-level fields. (i.e. via self)  
- **Cannot** define named workers or use async constructs (`start`, `future`)  
- **Cannot** use: `transaction`, `retry`, direct `method-call`, `function-call`, `action-call`  
- **Can** use: `activity-method-call-action`, `event-receive-action` (Defined later in this document)

##### Correlation Initialization

##### 

The execute method parameters define the correlation initialization:

| Scenario | Correlation Behavior |
| :---- | :---- |
| No parameters | Engine assigns a default correlation value (string) |
| Single parameter | `toString()` representation is the default correlation value |
| Multiple parameters | A **Resolver** must be provided  |

##### 

#### 3.3.2. Activity Methods {#3.3.2.-activity-methods}

Activity methods represent **atomic units of work** (computation or I/O).

Grammar: similar to `execute-method-decl` but without a resolver block.

##### Semantics

| Property | Specification |
| :---- | :---- |
| **Scope and isolation** | Defined in a separate symbol scope within the object. (Different from execute methods)Implicitly `isolated` |
| **State Access** | Cannot access mutable workflow state or module state.   |
| **Parameters** | Can only access their own parameters; must be subtypes of `anydata` |
| **Return Type** | Can return `anydata` type, including `error` |
| **Invocation** | Only callable from within the execute method |

#### 3.3.3. Event Methods

Event methods define two interfaces

* The **interface for receiving asynchronous signals** from external systems.  
* The interface, how the workflow accepts the signal

##### Semantics

| Property | Specification |
| :---- | :---- |
| **Parameters** | Must have at least one parameter; all must be subtypes of `anydata` |
| **Return Type** | Must return `anydata` including `error`; an error indicates failed event acceptance. |
| **Invocation** | Cannot be called directly within execute; use `event-receive-action` to wait on a signal |
| **External Access** | External clients can call event methods using the workflow identifier Implicitly `public` |

An optional `resolve` block is allowed after `method-defn-body`. For correlation mapping See section [Correlation and Resolvers](#4.-correlation-and-resolvers)

### 3.4 Workflow Actions {#3.4-workflow-actions}

The following are defined as part of the `actions` in the Ballerina spec.

#### 3.4.1 Activity Call Action (`->`)

Invokes an activity method. This semantically represents a boundary crossing from the "Orchestrator" to the "Worker".

`activity-method-call-action:`

```
self->activityName(args);
```

#### 3.4.2 Event Receive Action (`<-`)

Pauses execution and waits for an external signal targeted at a specific event method.

`event-receive-action:`

```
// Single Event Receive
result = self<-eventName;

// Alternative Event Receive (Pick - wait for any one)
result = self<-eventA | eventB;

// Multiple Event Receive (Join - wait for all)
results = self<-{eventA, eventB};
```

## 4\. Correlation and Resolvers {#4.-correlation-and-resolvers}

Correlation is the mechanism for mapping external data payloads to specific workflow instances. This is the same as defining a partner link in BPEL. 

**Design principle**: How to resolve correlation is something that workflow developer must know and it has to be part of the workflow logic. 

### 4.1 No Correlation {#4.1-no-correlation}

When the workflow has no event methods, correlation is not necessary. But the engine may assign a unique generated value for workflow instance identification.

### 4.2 Implicit Correlation {#4.2-implicit-correlation}

In case of Workflows has execute and have event methods with the same first parameter and it is a subtype of `string|int|decimal`, that parameter's `toString()` representation is used as the correlation key.   
This is convenient for simple scenarios. This value must be unique across all active workflow 	instances. When starting a new workflow instance, the same value returned by `toString()` of the first parameter will be used to identify the workflow instance.

```
// Execute: orderId becomes the correlation key
execute function start(string orderId) returns int { ... }

// Event: orderId becomes the correlation key
event function update(string orderId, Data payload) returns error? { ... }
```

### 4.3 Explicit Correlation Set (Resolvers) {#4.3-explicit-correlation-set-(resolvers)}

When the correlation key is nested within a record or requires custom logic, a **Resolver** block must be provided.

A resolver is a `block-statement` that:

- Can see the same arguments as the attached method  
- Returns a `string` (the correlation key)  
- Works as a pure function.

```java
workflow OrderFlow on engine {

    // Resolver for execute method
    execute function process(OrderRequest r) returns string {
        // Logic
    } resolve {
 // correlation key extraction  
        return r.id 
    }

    event function paymentReceived(string orderRef, decimal amount) returns PaymentMsg|error {
        // Event logic
    } resolve {
        // correlation key extraction
        return orderRef;
    }
}
```

## 5\. Workflow Declaration {#5.-workflow-declaration}

The workflow declaration binds a **Workflow Definition** (logic) to a concrete **Workflow Engine** (runtime) and makes it available to use in other integrations.

```
workflow <Identifier> on <WorkflowEngineExpression> {

    // Option 1: Include workflow class members directly
    // Fields, execute, activity, and event methods

    // Option 2: Spread from existing workflow class
    *WorkflowClass;

}
```

- The `Identifier` is a subtype of a `client object` representing the public interface of the workflow. The `Identifier` can be used to start workflows and send events.  
- No Init methods same as `service-declaration`  
- The `<WorkflowEngineExpression>` must evaluate to a workflow engine object type. This SPI is defined in the spec.  
- When the program starts, the engine instance is created and passed to the workflow declaration.  
- It desugars to the following code at module initialization:

```
var workflowLogic = workflow object { // workflow object construcor };
Engine engine = <WorkflowEngineExpression>;
var <Identifier> = engine.register(workflowLogic);
```

### 5.2 Workflow Client Interactions.  {#5.2-workflow-client-interactions.}

External actors interact with workflows using the remote method action call syntax (`->`). By defining a workflow declaration, or by registering a workflow definition with an engine, a user can obtain a workflow client object.

This client object exposes the execute and event methods as remote methods.

#### 5.2.1 Starting a Workflow Instance

The execute method becomes a remote method on the workflow client object. Invoking it starts a new workflow instance.

- Signature matches the execute method signature, except it returns the correlation key (string) or error.

```
// Returns the correlation key (string) or error
string pid = check workflowIdentifier->execute(data);
```

#### 5.2.2 Sending an Event

All event methods become remote methods on the workflow client object. Invoking an event method sends the event to the corresponding workflow instance. Correlation value is determined based correation resolver or implicit correlation rules.

- Signature matches the event method signature, except it returns `error?`.

```
// Returns error? (nil if successful)
check workflowIdentifier->eventName(data);
```

## 7\. Key Design Decisions. {#7.-key-design-decisions.}

### 7.1 Workflow Engine Syntactic Representation {#7.1-workflow-engine-syntactic-representation}

Options:

* **Option 1**  \- Event engine as part of `ballerina/workflow` (or `ballerina/lang.workflow`) library   
* **Option 2**  \- Decoupled engine supporting multiple implementations

This specification strongly favors a decoupled approach (Option 2). The core Ballerina language defines the type, syntax, and semantics, but delegates the actual state management, persistence, and execution scheduling to a pluggable **Workflow Engine**.

**Advantages of Option 1:**

- We can eliminate `<WorkflowEngineExpression>` and move engine configuration to configurable parameters of the workflow module.

**Problems with Option 1:**

- Tight coupling with the language core makes releasing new engine versions difficult. Always need to release a new Ballerina distribution.  
- This brings a lot of third-party dependencies into the core language distribution.  
- Language semantics depend on third-party vendors. So far, no language feature depends on third-party vendors, only protocols like transactions.  
- Language doesn't have any built-in configurables. 

Considering the above points, we recommend Option 2\. Align workflow declaration with the service-listener syntactic model and keep `<WorkflowEngineExpression>` to represent runtime binding. 

### 7.2 Why do we need an execute method qualifier? Why not a regular method with a special name like `main` function {#7.2-why-do-we-need-an-execute-method-qualifier?-why-not-a-regular-method-with-a-special-name-like-main-function}

- The approach establishes distinct semantics and symbol scope for activity and event methods.  
- The visibility of these methods is restricted to within the `execute` method.  
- Using regular methods would cause a collision with normal method semantics.  
- Regular methods would also allow calls originating outside the object, which we need to avoid.

### 7.3 Handling Breaking Changes.  {#7.3-handling-breaking-changes.}

The keyword `workflow` will be used in top-level constructs, which can cause issues with backward incompatibility. Other keywords can be modeled as contextually reserved keywords in a workflow context.

## 8\. Implementation Plan {#8.-implementation-plan}

  * No Events method, only execute and activities methods(But keep these reserved new keywords)  
  * Workflow Declaration Syntax

  * No sleep semantics  
  * Temporal as a workflow engine

* Support Event receives action

Phase 2 \- Examples.

A hospital runs a **diagnostic test workflow**:

1. A lab test is requested for a patient

2. Sample analysis is performed (activity)

3. Risk level is calculated (activity)

4. If risk is high → **wait for a doctor’s review signal**

5. After approval → generate the final medical report (activity)

```c#
import ballerinax/temporal;

type TestRequest record {|
    string testId;
    string patientId;
    string testType;
|};

type DoctorReview record {|
    string testId;
    boolean approved;
    string doctorId;
|};

workflow DiagnosticTestFlow on new temporal:Engine() {

    // ---- Workflow State ----
    string status = "REQUESTED";
    int riskLevel = 0;

    // ---- Execute Method ----
    execute function run(TestRequest req) returns string|error {
        self.status = "ANALYZING";

        // 1️⃣ Activity: Analyze lab sample
        int score = check self->analyzeSample(req.testType);
        self.riskLevel = score;

        // 2️⃣ Activity: Persist intermediate result
        check self->storePreliminaryResult(req.testId, score);

        // 3️⃣ Wait for doctor review if high risk
        if score > 60 {
            self.status = "WAITING_FOR_DOCTOR";

            DoctorReview review = check self<-doctorReviewed;

            if !review.approved {
                self.status = "REJECTED";
                return "Test rejected by doctor";
            }
        }

        // 4️⃣ Activity: Generate final report
        check self->generateReport(req.testId);

        self.status = "COMPLETED";
        return "Diagnostic test completed";
    } resolve {
        // Correlation by testId
        return req.testId;
    }

    // ---- Activity Methods ----

    activity function analyzeSample(string testType) returns int|error {
        // Call lab analysis system
        return 72;
    }

    activity function storePreliminaryResult(string testId, int score) returns error? {
        // Persist data to medical DB
        return ();
    }

    activity function generateReport(string testId) returns error? {
        // Produce PDF / EMR entry
        return ();
    }

    // ---- Event Method ----

    event function doctorReviewed(
        string testId,
        boolean approved,
        string doctorId
    ) returns DoctorReview|error {
        if doctorId == "" {
            return error("Doctor ID is required");
        }

        return {
            testId: testId,
            approved: approved,
            doctorId: doctorId
        };
    } resolve {
        return testId;
    }
}
```
